The 30-second pitch

DispatchX is a same-city parcel delivery platform, like Porter or Dunzo. A customer books a pickup and drop. Within a few seconds the system finds the nearest available rider, sends them the job, and once they accept, the customer watches the rider move on a live map. A dispatcher watches the whole city from an operations map and steps in when something goes wrong.

It runs on AWS as a set of Docker containers spread across two data centres (Availability Zones), behind CloudFront, a load balancer and a web application firewall. It scales up on its own under load and keeps working if a server dies. The entire infrastructure is written as code and deployed by a pipeline.

Why this is a cloud project and not just a web app: real-time traffic (hundreds of GPS pings per second) needs horizontal scaling, WebSockets across many servers, decoupled background processing and managed data stores. Those are exactly the Cloud Architecting topics: VPC design, elasticity, high availability, decoupling, caching, security and automation.

Life of one order

If you understand this flow you understand the project. Each step names the AWS service involved.

#What happensWhere it runs
1The customer opens the site. The request hits CloudFront (HTTPS, global edge network). Static files come from the edge cache; everything else goes to the Application Load Balancer, which checks a secret header so nobody can bypass CloudFront. AWS WAF on the ALB blocks SQL injection, bad inputs and floods.CloudFront → WAF → ALB
2The customer books. The API container (FastAPI on ECS) prices the trip, saves the order in RDS MySQL and publishes an order.created event to an SNS topic.ECS task in a private subnet, RDS in an isolated subnet
3SNS fans out the one event to three SQS queues: dispatch, notify and analytics. Each queue gets only the event types it cares about (subscription filter policies).SNS → SQS
4The consumer container reads the dispatch queue. It asks ElastiCache (Redis) "which online riders are within 3 km?" using Redis geo-search, scores them on distance and rating, and offers the job to the best one with a 20-second timer.ECS consumer + ElastiCache
5The offer reaches the rider's phone instantly over Socket.IO (WebSockets). If they ignore it, a Celery timer task moves on to the next rider. If they decline, it goes straight to the next. Nobody can be double-booked, thanks to Redis locks and an atomic database update.ECS worker + Redis
6The rider accepts. Their GPS position streams every 2 seconds; the customer and the dispatcher see the rider move live. This works even though they may be connected to different API servers, because every server shares messages through Redis pub/sub.Socket.IO + Redis adapter
7At delivery the rider uploads a photo directly to S3 using a short-lived presigned URL, so the image never passes through our servers. S3 emits an event to EventBridge, which triggers a Lambda that validates and tags the photo.S3 → EventBridge → Lambda
8Every status change also lands in the analytics queue. A second Lambda writes those events into an S3 data lake, where Athena can query them with SQL (orders per hour, assignment times, top riders).SQS → Lambda → S3 → Glue → Athena
9Throughout, CloudWatch collects logs, metrics and alarms, and Prometheus + Grafana show live business metrics. If error rates spike or messages fail, an alarm emails the team through SNS.CloudWatch, Grafana

Security in depth

Examiners like layered security. DispatchX has a control at every layer:

  • Edge: HTTPS everywhere via CloudFront, managed security headers (HSTS, no-sniff, frame options).
  • Origin protection: the ALB security group only accepts CloudFront's IP ranges, and the ALB rejects any request without CloudFront's secret X-Origin-Verify header (direct hits get 403).
  • Web firewall: AWS WAF with AWS-managed rule sets (common exploits, known bad inputs, SQL injection) plus per-IP rate limiting.
  • Network: private app subnets, isolated data subnets, chained security groups, a NACL on the data tier.
  • Identity: separate IAM roles for EC2 hosts, ECS task execution, the app's tasks and each Lambda, each with only the permissions it needs (for example, the app may only write to pod/* in one bucket and only publish to two topics).
  • Secrets: database password, JWT signing key and Grafana password are generated by Secrets Manager and injected into containers at start-up. None of them appear in code or in the repository.
  • Data: encryption at rest on RDS, ElastiCache, EBS, S3 and SQS; an S3 bucket policy denies non-HTTPS access.
  • Application: JWT access and refresh tokens, role-based access (customer, rider, dispatcher, admin), bcrypt password hashing.
  • Instances: IMDSv2 required, no SSH keys; shell access goes through Systems Manager Session Manager.

Scaling and high availability

  • Two Availability Zones for subnets, EC2 hosts and containers (ECS spreads tasks across AZs).
  • Service auto scaling: the api service targets 60% CPU and grows from 2 to 8 tasks; the consumer scales on SQS queue depth (the classic "scale workers on backlog" pattern); the worker scales on CPU.
  • Cluster auto scaling: when new tasks do not fit, the ECS capacity provider launches more EC2 instances (2 → 4).
  • Self-healing: ALB health checks remove sick containers; ECS replaces stopped tasks; the Auto Scaling group replaces failed instances.
  • Safe deploys: rolling updates with the ECS deployment circuit breaker, which rolls back automatically if new containers fail health checks.
  • Stateless app tier: no state lives inside a container. WebSocket messages go through Redis, so any API server can serve any user. That is what makes horizontal scaling possible.
  • Data tier HA (toggle): RDS Multi-AZ standby and an ElastiCache replica with automatic failover, switched on from the pipeline for the demo (off by default to save credits).
  • Disaster recovery: automated RDS backups, S3 versioning, optional final snapshot on teardown, and the whole environment can be rebuilt from code in about 25 minutes.

Docker and Kubernetes

Docker: every component (API, web frontend, workers, Prometheus, Grafana) is a Docker image. Locally the whole system runs with one docker compose up; on AWS, ECS runs the same images.

Kubernetes: the k8s/ folder runs the same images on a 3-node Kubernetes cluster (kind, Kubernetes-in-Docker). It uses Deployments, a StatefulSet for MySQL with a persistent volume, Services, an NGINX Ingress, HorizontalPodAutoscalers, RBAC and a Job for seeding. GitHub Actions builds this cluster and runs the end-to-end test on it on every push.

Visualising it: the app's Cluster page draws the live cluster, whichever platform it runs on: EC2 instances and ECS tasks on AWS, or nodes and pods on Kubernetes. You can stop a container from that page and watch the orchestrator replace it.

Viva questions

Why did you use CloudFront if you already have a load balancer?

CloudFront gives HTTPS without buying a domain or certificate, caches static assets at edge locations close to users, absorbs traffic spikes, and hides the ALB: the ALB only accepts CloudFront's IP ranges and its secret header. The ALB then spreads requests across containers.

How do WebSockets work with many servers behind a load balancer?

Each API server runs a Socket.IO server connected to a shared Redis pub/sub channel. When a rider's GPS ping arrives at server A, it is published to Redis, and server B delivers it to the customer connected there. The ALB has a 120-second idle timeout and sticky sessions for the long-polling fallback.

Why SNS plus SQS, and not just SQS?

That is the fan-out pattern. One order.created event must reach three independent consumers (dispatch, notifications, analytics). SNS copies it to each queue, and each queue buffers work so a slow or failed consumer does not affect the others. Filter policies make each queue receive only the event types it needs.

What is a dead-letter queue and why do you need one?

If a message fails processing 5 times, SQS moves it to a separate DLQ instead of retrying forever. That keeps the main queue flowing and preserves the bad message for debugging. A CloudWatch alarm emails us as soon as anything lands in a DLQ.

How do you avoid assigning one order to two riders?

Three layers. A Redis SET NX lock per rider means a rider never sees two offers at once. A per-order dispatch lock makes duplicate SQS deliveries harmless. Acceptance is a conditional SQL update (WHERE status = 'pending'), so only the first accept succeeds.

Why Redis for finding nearby riders?

Redis has built-in geospatial indexes. GEOSEARCH returns riders within a radius, sorted by distance, in under a millisecond, entirely in memory. Querying MySQL for that on every ping would be far slower. The search radius widens from 3 to 6, 12 and 25 km on retries.

How does auto scaling work here?

Two levels. ECS service auto scaling adds API tasks when average CPU goes above 60%, and consumer tasks when the dispatch queue backs up. When new tasks do not fit on the existing instances, the ECS capacity provider tells the Auto Scaling group to launch more EC2 instances, up to 4.

What happens if an Availability Zone goes down?

Subnets, instances and containers are spread across two AZs, so the ALB keeps routing to the surviving zone and ECS reschedules tasks there. With Multi-AZ enabled, RDS fails over to its standby in about a minute and ElastiCache promotes its replica. The app reconnects automatically (connection pre-ping and recycling).

Why are the databases in subnets with no internet access?

The database never needs to talk to the internet, so its route table has no default route at all. Even a misconfigured security group could not expose it publicly. Only ECS hosts can reach it, on one port.

Security group or network ACL: what is the difference?

Security groups are stateful and attach to resources (return traffic is allowed automatically). NACLs are stateless and attach to subnets (you must allow return traffic explicitly). We use security groups as the main control and a NACL on the data tier as a second layer.

Where are passwords stored?

Secrets Manager generates the database password, JWT key and Grafana password. ECS injects them into containers as environment variables at start-up using the task execution role. They never appear in Git, the templates or the container images.

Why upload photos straight to S3?

The API generates a presigned URL valid for 5 minutes for one object key. The browser uploads directly to S3, so large files never load our servers, and S3 scales without limit. An EventBridge rule then triggers a Lambda that validates the file type and size and tags the object.

What is infrastructure as code and why does it matter?

The infrastructure is described in CloudFormation templates kept in Git. Deployments are repeatable, reviewable and versioned; we can rebuild the identical environment in another account or region, and tear it all down with one command. Nested stacks keep each layer separate and reusable.

What does your CI/CD pipeline check?

It lints the templates (cfn-lint) and checks the wiring between nested stacks, runs unit tests, runs a full end-to-end order test, builds and pushes four images, deploys CloudFormation, seeds data with an ECS one-off task, and runs the end-to-end test again against the live CloudFront URL. On failure it prints the CloudFormation errors and container logs.

How do you monitor it?

CloudWatch handles infrastructure: ALB requests, latency and errors, ECS CPU and task counts (Container Insights), RDS, ElastiCache and SQS metrics, logs from every container, and 10 alarms that email the team. Prometheus and Grafana show application metrics such as orders per minute, offer outcomes and average assignment time.

Why ECS on EC2 instead of Fargate?

The syllabus emphasises the EC2 compute layer, and ECS on EC2 shows both levels of scaling (tasks and instances) plus the capacity provider. Bin-packing several small containers onto two instances is also cheaper for an always-on demo. Fargate would remove instance management at a higher per-task price.

What does it cost to run?

About $4–5 per day in Sydney: EC2 hosts, the NAT Gateway and the ALB are the biggest items. We only run it when needed and destroy it with one workflow; it all came out of the account's free credits.

How would you make it production-grade?

Enable RDS Multi-AZ and the ElastiCache replica permanently, a NAT Gateway per AZ, a custom domain with ACM certificate, OIDC instead of an access key for CI, AWS Backup with cross-region copies, and EKS or Fargate depending on team skills.
